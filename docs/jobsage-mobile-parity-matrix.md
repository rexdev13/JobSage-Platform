# JOBSAGE web-to-mobile route and role parity

**Source checked:** 12 October 2026; employer organization and staff details rechecked 13 October 2026. This matrix describes repository behavior; it is not a physical-device acceptance record.

## Shared routing and access rules

- The website route source is `artifacts/jobsage-web/src/App.tsx`; role-specific navigation is in `components/layout/AppSidebar.tsx` and `lib/candidateNavigation.ts`.
- The native app root redirects to `/workspace`. `workspace` loads the canonical website in a first-party WebView; `?path=` is accepted only after `safeInternalPath` rejects external origins, `//`, backslashes, control characters, and encoded CR/LF or backslash.
- `/login` is a native login screen. Other website routes, including registration, onboarding, public legal pages, employer pages, and operations screens, open through the canonical WebView route. Five native companion screens are available at `/companion`, `/companion/applications`, `/companion/analytics`, `/companion/path`, and `/companion/profile`.
- The native companion layout now allows only `candidate`; unauthenticated users go to `/login`, and every other signed-in role returns to `/workspace`. Cold/warm custom-scheme routing has not been verified on physical devices.
- `app.json` declares `jobsage-mobile`, but no iOS Associated Domains or Android verified App Links are configured. The source has no push-notification route parser or active push-delivery workflow. `/privacy/push-device` is an API foundation, not proof of native push delivery.
- `AuthGuard` allows public paths, requires a signed-in user for other routes, and redirects `marketing` users to `/admin/leads` except on `/admin/leads` and `/admin/calendar`. API `requireAuthenticated` also rejects marketing users and denies writes during impersonation. `requireRole` enforces explicit roles server-side.
- Employer access is organization-scoped and separate from global account roles. The five organization roles are `employer_owner`, `employer_admin`, `recruiter`, `hiring_manager`, and `employer_viewer`; active membership and, for limited staff, job assignment are checked by the API. The web guard uses the active organization role. Current development schema drift means this source behavior is not runtime acceptance.
- API endpoints below are the primary operations used by each page, not an assertion that every secondary request has been exhaustively enumerated. OpenAPI source is `lib/api-spec/openapi.yaml`.

## Navigation and feature status

- Candidate labels/order are unchanged: `My Profile`, `My UK Opportunities`, `UK Career Journey`, `Career Readiness`, `Insights`, `Support`, with the labels listed in `CANDIDATE_NAVIGATION`. Unread Messages uses the account-scoped unread-count endpoint; candidate profile-photo and logout controls remain in the sidebar.
- Reviewer/admin navigation includes the existing review queue and legacy candidate operational views. Employer/admin navigation includes employer dashboard, posting, talent search, campaigns, organisation profile, and staff management. Marketing sees Waitlist Leads and Calendar. Super-admin-only routes remain separate.
- Organization membership roles are separate from global account roles. Limited staff access is restricted to assigned jobs and explicit capabilities; no global `employer_staff` role is required.
- Native companion role gating has render coverage for candidate, employer, reviewer, admin, super-admin, marketing, and null roles. The web employer route allowlist and API role/assignment middleware have source tests. There is not yet a complete browser/device test of every matrix row, and the development schema is not ready for staff-route runtime acceptance.
- Feature-name parity is implemented through the canonical WebView, not duplicated native pages. Only the five companion tabs are native substitutes, and those are partial views. This is source parity, not evidence of acceptable physical-device interaction for every workflow.
