BUG TO FIX

In the installed Android APK:

1. The user can open the app and sign in.
2. The initial JOBSAGE workspace loads successfully.
3. The user selects another page from the website sidebar.
4. The full-screen JOBSAGE splash/loading overlay appears again.
5. On Android, that overlay can remain indefinitely even though the underlying SPA route has changed.

This does not reproduce reliably in Expo Go.

LIKELY ROOT CAUSE

Inspect `artifacts/jobsage-mobile/app/workspace.tsx`.

The affected implementation uses a simple boolean such as:

- `pageLoading`
- `setPageLoading(true)` inside `onLoadStart`
- `setPageLoading(false)` only inside `onLoadEnd`
- A full-screen loader rendered whenever `pageLoading` is true

Android WebView can emit `onLoadStart` during client-side SPA/sidebar navigation without producing the matching `onLoadEnd` expected by that boolean logic. The loader then covers an already usable workspace forever.

REQUIRED BEHAVIOUR

The blocking JOBSAGE loader may appear only:

- While the first workspace document is becoming usable.
- When the user explicitly presses Retry after a genuine failure.

After the workspace has become usable once:

- A normal SPA/sidebar navigation must not restore the blocking loader.
- A later `onLoadStart` must not move a ready workspace back into a blocking state.
- The underlying page must remain visible during internal route changes.
- Genuine initial-load and render-process failures must still display the existing error/retry UI.
- Retry must deliberately restore the blocking loader while the WebView reloads.
- A late load callback must not hide an already recorded failure.

IMPLEMENTATION APPROACH

Create a small, pure loading policy module, preferably:

`artifacts/jobsage-mobile/lib/workspace-load-policy.ts`

Use these states:

- `waiting`
- `blocking`
- `ready`
- `failed`

Use events equivalent to:

- `source-ready`
- `navigation-start`
- `content-visible`
- `complete`
- `retry`
- `failure`

The required state transitions are:

- `waiting + source-ready` → `blocking`
- `waiting + navigation-start` → `blocking`
- `blocking + content-visible` → `ready`
- `blocking + complete` → `ready`
- `ready + navigation-start` → remain `ready`
- Any valid state + explicit `retry` → `blocking`
- Any state + `failure` → `failed`
- `failed + complete/content-visible` → remain `failed` until explicit retry

Export a helper that returns true only when the state is `waiting` or `blocking`.

Integrate this state machine into `app/workspace.tsx` using `useReducer` or an equivalent deterministic implementation.

Integration requirements:

1. Replace the fragile `pageLoading` boolean.
2. Start the initial timeout only while there is a source, no load error, and the policy is blocking.
3. Keep the existing 30-second initial load timeout or its current equivalent.
4. Dispatch `navigation-start` from WebView `onLoadStart`.
5. Dispatch `content-visible` when `onLoadProgress` reaches a reasonable usable threshold, approximately `0.8`.
6. Dispatch `complete` from `onLoadEnd`.
7. Dispatch `failure` before recording genuine WebView load/render failures.
8. Dispatch `retry` inside the explicit retry handler before remounting/reloading the WebView.
9. Render the full-screen JOBSAGE loader only when the policy reports a blocking phase and there is no load error.
10. Give the loader `pointerEvents="none"` so it cannot trap input during transitions.
11. Preserve the current JOBSAGE branding and loader appearance.
12. Preserve session exchange, cookies, native bridge injection, deep links, external-link policy, Android back handling, downloads, push notifications and every other current behaviour.

Do not solve this by adding arbitrary delays, hiding every loader, disabling navigation events, or forcing every sidebar route into an external browser.
